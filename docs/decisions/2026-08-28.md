# Decisions — 2026-08-28

## D-2026-08-28-01 — Scope OpenClaw prompt caching to each Lead Finder run
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Route every persisted Lead Finder step in a run through one deterministic, hashed OpenClaw `user` session and expose normalized cached-token metrics on steps and attempts.
- **Why:** OpenClaw's Chat Completions endpoint maps `user` to the stable session and downstream cache key, while caller-supplied raw cache fields are not part of that compatibility endpoint's accepted transport contract. Per-run scoping enables growing-prefix reuse without sharing agent history across runs, and measured cached tokens distinguish real hits from configuration intent.
- **Refs:** `app/services/lead_finder.py`, `app/services/llm_gateway.py`, `frontend/app/lead-finder/page.tsx`

## D-2026-08-28-02 — Make prompt-cache-aware context design a project rule
- **Area:** process
- **Status:** accepted
- **Decision:** Require recurring agent contexts to lead with a stable reusable prefix, place volatile state afterward, scope cache/session identities to genuinely related requests, and verify cache use from provider usage metrics.
- **Why:** Context layout and transport identity determine whether caching can work; configuration flags alone can be ignored by compatibility layers and do not prove a cache hit.
- **Refs:** `CLAUDE.md`

## D-2026-08-28-03 — Stage Lead Finder results through transcript evidence and person research
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Restrict initial candidate discovery to Mission Control transcripts, allow public-web research only after exact transcript evidence identifies a person, and require a later explicit tool call to add that completed research to the run-local Found Leads list. Defer deduplication and all CRM writes.
- **Why:** This creates the narrowest inspectable learning loop: discovery provenance is controlled, current outreach relevance can still be verified, and research cannot silently become an accepted lead in the same step.
- **Refs:** `app/services/lead_finder_tools.py`, `app/services/lead_finder_web_research.py`, `frontend/app/lead-finder/page.tsx`

## D-2026-08-28-04 — Send immutable Lead Finder context once per OpenClaw run session
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Put deterministic job, tool, and baseline content before mutable run state on the first gateway turn, exclude volatile snapshot timestamps from that prefix, and omit the immutable block from continuation turns in the same run-scoped OpenClaw session.
- **Why:** Prefix caching cannot reuse a large baseline placed after changing state, and resending that baseline on every appended session turn adds uncached input without adding information. The OpenClaw session already retains the first turn; continuation requests need only authoritative mutable state.
- **Refs:** `app/services/lead_finder.py`, `app/skills/lead-finder/SKILL.md`, `tests/test_lead_finder.py`

## D-2026-08-28-05 — Expose OpenClaw session context in its native JSONL
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Give the Lead Finder an operator-only raw-session view backed directly by OpenClaw's canonical session and trajectory JSONL files, without normalizing their records into a Possible OS message schema.
- **Why:** Debugging the actual model context requires the source OpenClaw stores, including compiled system prompts and runtime snapshots; a reconstructed view could hide ordering, compaction, or injected context. The raw files are unredacted and must be treated as sensitive.
- **Refs:** `GET /api/lead-finder/runs/{run_id}/llm-session`, `lead-finder llm-session`, `frontend/app/lead-finder/page.tsx`
