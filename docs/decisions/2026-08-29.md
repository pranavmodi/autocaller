# Decisions — 2026-08-29

## D-2026-08-29-01 — Use one recursive JSON viewer across Lead Finder debug data
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Reuse the expandable syntax-highlighted JSON tree for every structured Lead Finder debug surface and recursively decode valid object/array JSON found inside string fields for presentation only.
- **Why:** Gateway messages and assistant outputs often contain serialized JSON inside strings; leaving those values escaped makes the real context difficult to inspect, while changing the persisted representation would compromise raw fidelity.
- **Refs:** `frontend/app/lead-finder/page.tsx`

## D-2026-08-29-02 — Persist bounded Lead Finder auto-run state on the run
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Unattended Lead Finder execution chains the existing durable one-transition steps from server-persisted run state, with operator stop and a bounded additional-step budget, rather than relying on a browser loop.
- **Why:** The run must continue and recover without an open browser while preserving the same inspectable reasoning/tool boundary and preventing manual and automatic next-step races.
- **Refs:** `app/services/lead_finder.py`, `lead_finder_runs.auto_run_*`

## D-2026-08-29-03 — Make Lead Finder web research transport selectable per run
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Default `web.research_person` to a direct OpenAI Responses API call using `gpt-5.6-luna`, while retaining `openclaw/main` as an operator-selectable per-run fallback. Keep the Lead Finder reasoning loop itself on its existing isolated OpenClaw session.
- **Why:** Direct Responses API web search removes the shared OpenClaw main-lane queue from the slow research path, while the persisted switch preserves a fallback and separates transport experiments from the agent's reasoning/session semantics.
- **Refs:** `app/services/lead_finder_web_research.py`, `lead_finder_runs.web_research_provider`, `PUT /api/lead-finder/runs/{run_id}/web-research-provider`

## D-2026-08-29-04 — Make the Lead Finder provider selection run-wide
- **Area:** lead-gen
- **Status:** accepted; supersedes D-2026-08-29-03
- **Decision:** The per-run provider now controls every Lead Finder LLM call. `openai` routes reasoning and web research directly through the Responses API with `gpt-5.6-luna`; `openclaw` routes both through `openclaw/main`. Mission Control remains a local non-LLM tool API.
- **Why:** A selector labeled Direct OpenAI should not leave reasoning queued on OpenClaw. Run-wide semantics make transport, latency, cost, and debugging behavior predictable while retaining explicit fallback.
- **Refs:** `lead_finder_runs.llm_provider`, `app/services/lead_finder_provider.py`, `PUT /api/lead-finder/runs/{run_id}/llm-provider`

## D-2026-08-29-05 — Repair malformed OpenClaw structured output once before failing
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Lead Finder OpenClaw calls persist the exact invalid assistant content and partial parse, then make one bounded schema-repair request that preserves the intended transition before declaring the step failed.
- **Why:** OpenClaw JSON formatting is prompt-constrained rather than mechanically enforced; a single misplaced brace should not discard an otherwise valid transition, but unbounded retries could duplicate cost or agent work.
- **Refs:** `app/services/llm_gateway.py`, `LEAD_FINDER_GATEWAY_SCHEMA_REPAIR_RETRIES`
