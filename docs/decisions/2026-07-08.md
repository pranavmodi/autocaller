## D-2026-07-08-01 — Resolve LinkedIn profiles on demand
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Resolve personal LinkedIn URLs demand-driven per contact or per lead-gen batch, writing only validated `linkedin.com/in/` URLs to the existing `firm_contacts.linkedin_url` column.
- **Why:** This avoids re-enriching the full firm universe while improving direct-profile coverage exactly where outbound operators are preparing a wave.
- **Refs:** `app/services/linkedin_resolver.py`, `contacts resolve-linkedin`, `contacts resolve-linkedin-batch`

## D-2026-07-08-02 — Operator-settable email transport strategy (deliverability lever)
- **Area:** deliverability
- **Status:** accepted
- **Decision:** Add a first-class lever to choose the lead-gen email send order (`zoho_first_then_resend` default vs `resend_first_then_zoho`) and per-provider daily caps on the active policy, exposed as `set_lead_gen_transport` → `PUT /api/lead-gen/settings/transport` → `lead-gen transport` CLI + `/lead-gen` UI. `set_daily_send_budget` now preserves an operator-set strategy/Zoho cap instead of resetting to defaults.
- **Why:** Live A/B on Wave 2 showed Resend (from `getpossibleminds.com`) lands in the inbox while the Zoho path (from `possiblemindshq.com`, shared Zoho India IP `103.117.158.11`) lands in junk — and the default `zoho_first` strategy silently filled the junk path first. This makes the channel choice controllable and scriptable per CLI-parity. This *supersedes* the earlier "keep Zoho, not Resend" lean: Zoho's Gmail-Primary placement in the seed test proved fragile (slid to junk within hours). Live config left at the default for now; flipping to Resend-first is gated on confirming Resend's account send limit.
- **Refs:** `app/services/lead_gen_cybernetic.py` (`set_lead_gen_transport`), `app/api/lead_gen.py`, `app/cli.py` (`lead-gen transport`), `docs/LEAD_GEN_CYBERNETIC_TECHNICAL.md`

## D-2026-07-08-03 — CLI email sends require an explicit transport; per-send override is authoritative
- **Area:** deliverability
- **Status:** accepted
- **Decision:** Every CLI email-send command (`actions send-email`, `actions send-test-email`, `actions send-approved-lead-gen-draft`) now **requires** `--transport` (`resend` | `zoho_api`); the value is validated, echoed in output, threaded through the request models + `create_send_email_action` / `create_send_approved_lead_gen_draft_action` into the action `input_json`, and honored authoritatively in `_execute_send_email` / `send_batch_item_draft` (skips the policy transport strategy). Automatic strategy selection now applies only when no explicit transport is set (daily-run / agent-slice paths). Standing guidance: use `resend` for all manual sends until Zoho deliverability is fixed.
- **Why:** An operator sending a wave must never have the provider chosen opaquely behind their back — the Wave 2 junk problem was invisible precisely because the CLI silently filled Zoho first. Requiring the transport makes the deliverability-critical choice explicit and auditable per email. Complements D-2026-07-08-02 (policy-level default) with a per-send lever.
- **Refs:** `app/services/action_execution.py`, `app/services/lead_gen_cybernetic.py` (`send_batch_item_draft`), `app/api/actions.py`, `app/cli.py` (`_validate_transport`), `docs/cli.md`, `SKILL.md`
