# Decisions — 2026-08-27

## D-2026-08-27-01 — Lead Finder starts as a one-step reasoning debugger
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Load the four business-context files and fixed Lead Finder job by default, add the user's run-specific lead direction to context, and run one stateless `openclaw/main` reasoning transition per explicit debug trigger. Defer source tools and durable server-side run state.
- **Why:** This makes the context and LLM boundary inspectable before adding searches, databases, or autonomous execution.
- **Refs:** `app/services/lead_finder.py`, `frontend/app/lead-finder/page.tsx`

## D-2026-08-27-02 — Persist Lead Finder execution before adding source tools
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Replace browser-owned Lead Finder history with Postgres-backed runs, steps, and per-attempt gateway traces. Queue each debug step asynchronously with idempotency and one-active-step protection; restarting creates a linked step-0 run rather than erasing history. This supersedes D-2026-08-27-01's deferral of durable run state.
- **Why:** Operators must be able to inspect queued and in-flight work independently of the browser, distinguish retries from duplicate clicks, and reproduce exactly which context produced a response.
- **Refs:** `alembic/versions/x3y4z5a6b7c8_add_lead_finder_runs.py`, `app/services/lead_finder.py`

## D-2026-08-27-03 — Make full Lead Finder reset explicit and atomic
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Add a separately confirmed reset operation that deletes all Lead Finder runs, steps, and gateway attempts and creates one fresh step-0 run in the same database transaction. Scope deletion only to Lead Finder history; late responses from already in-flight deleted steps are discarded.
- **Why:** The debug workspace needs a predictable clean-slate control without leaving a no-run state or risking unrelated lead and outreach data.
- **Refs:** `app/services/lead_finder.py`, `app/api/lead_finder.py`, `frontend/app/lead-finder/page.tsx`

## D-2026-08-27-04 — Expose Mission Control search as persisted read-only agent tools
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** Keep transcript indexing and retrieval in Mission Control and expose only its HTTP API to Possible OS through three validated read-only Lead Finder tools: hybrid/keyword/semantic search, exact passage fetch, and index status. Permit at most one tool request per debug step, persist the request/result/error in Postgres, add it to bounded working context, and pause. Do not expose Mission Control SQLite or index mutations.
- **Why:** This gives the agent real source evidence with an inspectable execution boundary while preserving data ownership, reproducibility, and the one-step debugger contract.
- **Refs:** `app/services/mission_control_search.py`, `app/services/lead_finder.py`, `alembic/versions/y4z5a6b7c8d9_add_lead_finder_tool_calls.py`
