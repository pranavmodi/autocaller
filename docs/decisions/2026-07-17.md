# 2026-07-17

## D-2026-07-17-01 — Allow authenticated operators to replace the returned-data script
- **Area:** infra
- **Status:** accepted; supersedes D-2026-07-15-01
- **Decision:** Keep `GET /datareturned/script` public, but allow authenticated dashboard users and the loopback CLI to persist the exact script it serves. Retain the fixed read-only diagnostic as the default before the first save.
- **Why:** The returned-data workflow now needs operator-controlled diagnostics without requiring a deploy for each script change. Restricting writes to authenticated or loopback access keeps mutation off the public surface, while the editor warns that saved text is executable and publicly retrievable.
- **Refs:** `app/api/data_returned.py`, `app/services/data_returned.py`, `/data-returned`, `data-returned save-script`

## D-2026-07-17-02 — Preserve returned-data scripts when switching them to no-op
- **Area:** infra
- **Status:** accepted
- **Decision:** Persist an enabled flag separately from the operator-managed script. When disabled, keep `GET /datareturned/script` available but return a successful `exit 0` no-op; re-enabling restores the exact saved script.
- **Why:** Operators need an immediate reversible execution stop without editing, deleting, or later reconstructing the diagnostic script or changing the fetch-and-run integration.
- **Refs:** `/data-returned`, `data-returned script-on|script-off`, `PUT /api/datareturned/script/enabled`

## D-2026-07-17-03 — Keep a visible empty heartbeat while returned-data is in no-op mode
- **Area:** infra
- **Status:** accepted; supersedes D-2026-07-17-02's `exit 0` response behavior
- **Decision:** In No-op mode, serve a minimal script that posts exactly `{}` to `/datareturned` instead of exiting without a callback. Continue preserving the operator's full saved script separately.
- **Why:** Operators need proof that the remote fetch, execution, and callback path is still alive even while diagnostic and database commands are disabled.
- **Refs:** `build_data_returned_noop_script`, `/data-returned`, `data-returned script-off`

## D-2026-07-17-04 — Hard-cap returned-data history at 100 events
- **Area:** data-arch
- **Status:** accepted
- **Decision:** Retain only the newest 100 `/datareturned` callback events. Prune older events in the same transaction as every new insert and expose an authenticated immediate prune command for existing history.
- **Why:** The callback surface is an operational diagnostic, not a long-term event archive; a hard cap keeps the UI and table bounded while preserving the most relevant recent runs.
- **Refs:** `record_data_returned`, `data-returned prune`, `POST /api/datareturned/prune`
