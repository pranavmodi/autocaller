# Decisions - 2026-08-26

## D-2026-08-26-01 - Own web research locally
- **Area:** data-arch
- **Status:** accepted
- **Decision:** EmailTag is no longer a web-research execution backend. Possible OS features that need web search must execute and persist that research locally; existing EmailTag research relays must be migrated before use.
- **Why:** EmailTag web search is disabled, while the Possible OS server has a loopback OpenClaw gateway and a local durable store.
- **Refs:** `PROJECT.md`, `CLAUDE.md`, `app/services/pif_job_posting_research.py`

## D-2026-08-26-02 - EmailTag ends at raw PIF extraction
- **Area:** data-arch
- **Status:** accepted
- **Decision:** EmailTag publishes a cursor-based raw extraction feed only. Possible OS preserves that source payload, owns canonical identity and all derived research, and queues changed firms into its durable local enrichment workers during daily delta sync.
- **Why:** One local owner prevents remote auth/research outages from breaking Leads and keeps derived state queryable without upstream calls.
- **Refs:** `app/services/firm_intel_sync.py`, `app/services/pif_local_enrichment.py`, `app/api/pif.py`

## D-2026-08-26-03 - Make local firm enrichment staged and non-destructive
- **Area:** data-arch
- **Status:** accepted
- **Decision:** Full firm enrichment persists stage-level progress in the durable task and firm record, completes only after all local stages finish, and merges new facts into existing research rather than replacing collections with empty or partial results.
- **Why:** Operators need recoverable progress and visible failures, while repeated or degraded research must not erase previously verified firm intelligence.
- **Refs:** `app/services/pif_local_enrichment.py`, `app/services/pif_local_derivations.py`, `frontend/app/emailtag-firms/page.tsx`

## D-2026-08-26-04 - Alert only on confirmed campaign engagement
- **Area:** lead-gen
- **Status:** accepted
- **Decision:** The cross-campaign feed may expose scanner and unconfirmed signals for diagnosis, but operator toast and opt-in desktop alerts fire only for events classified as human by the existing page-session quality rules.
- **Why:** Redirect scanners are common in email and LinkedIn delivery paths; notifying on raw fetches would create false buying-intent signals.
- **Refs:** `app/services/engagement_campaigns.py`, `frontend/components/EngagementNotificationPopup.tsx`, `frontend/app/click-analytics/page.tsx`
